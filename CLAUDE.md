# CLAUDE.md

Guidance for Claude Code working in this repository. Read the [README](README.md) for the
user-facing picture; this file covers the things that are easy to get wrong.

## What this is

A practice-tool overlay for Dark Souls: Remastered. A DLL is injected into the running game, hooks
DX11 `Present` via `hudhook`, and draws an ImGui overlay that reads and writes game memory.

Windows x64 only. MSVC toolchain. Rust 1.88+ (`rustup update stable` if cargo complains a dependency
needs newer rustc).

## Workspace layout

| Crate | Role |
| --- | --- |
| `lib/libdsr` | Game-specific memory access: pointer chains, bitflags, generated base addresses. No UI. |
| `tool` | Two artifacts from one crate — the injector binary (`main.rs`, `inject.rs`) and the overlay cdylib (`lib.rs`, `tool.rs`, `config.rs`, `widgets/`). |
| `xtask` | AOB-scan code generator. Run with `cargo xtask`. |

## Commands

```sh
cargo build --release      # both the injector .exe and the overlay .dll
cargo check                # fastest correctness loop
cargo test -p dark_souls_remastered_tool   # config parse tests only
cargo +nightly fmt         # rustfmt.toml uses nightly-only options
cargo xtask                # regenerate base_addresses.rs (needs the game + .env)
```

## Hard rules

**Never hand-edit `lib/libdsr/src/codegen/base_addresses.rs`.** It is generated by `cargo xtask` and
says so at the top. To change what it contains, edit the AOB signature list in
`xtask/src/codegen/aob_scans.rs` and regenerate.

**Do not "optimise" `memedit.rs` to dereference raw pointers.** Every pointer-chain hop deliberately
goes through `ReadProcessMemory` even though the DLL runs inside the target process. Practice tools
read pointers that are legitimately invalid all the time — there is no player object on the main menu
— and this is what turns an access violation that kills the game into a `None`. It is the single most
important design decision in the codebase.

**Commented-out code here is scaffolding, not rot.** `tool/src/config.rs` has large commented blocks
(`ItemSpawner`, `OpenMenu`, `Quitout`, `Target`, most render flags) and `tool/src/widgets/` has
modules not yet wired in. `dark_souls_remastered_tool_complete.toml` is the target config for all of
it. Do not delete any of this as dead code — it is the roadmap. Same for
`tool/src/widgets/item_ids.json`, which is data waiting on the item spawner.

**Keep `[patch.'crates-io']` in the workspace root `Cargo.toml`.** Cargo silently ignores `[patch]`
in member manifests. It pins `imgui` to a git rev that `hudhook` 0.7 needs.

**`Cargo.lock` is committed on purpose** — this workspace ships executables. Do not re-add it to
`.gitignore`.

**Never commit `.env`.** It holds a machine-specific game path. `.env.example` is the tracked
template.

## Adding a feature

A new toggle or widget touches four places, in this order:

1. **`lib/libdsr/src/pointers.rs`** — add the chain to `PointerChains` with `pointer_chain!` or
   `bitflag!`. If it needs a new base address, add the AOB to `xtask/src/codegen/aob_scans.rs` first
   and regenerate.
2. **`tool/src/widgets/<name>.rs`** — a thin adapter implementing the relevant `practice-tool-core`
   trait (`ReadWrite`, `Flag`, `Stats`, `PositionStorage`, …) plus a constructor returning
   `Box<dyn Widget>`. Look at `souls.rs` for the minimal shape.
3. **`tool/src/widgets/mod.rs`** — declare the module.
4. **`tool/src/config.rs`** — add a `CfgCommand` variant (or a `FlagSpec` arm for a plain bitflag)
   and the matching `into_widget` arm.

Then document it: the Features table and the Commands table in the README, and the shipped
`dark_souls_remastered_tool.toml` if it deserves a default hotkey.

## Verification limits — read this before claiming something works

`cargo check` proves it compiles. **It proves nothing about whether the pointers are right.** Offsets,
bitmasks, and pointer chains can only be confirmed by injecting into a running game and looking at
the result.

So: do not report a memory-facing change as working or tested. Say it compiles, and say what the user
needs to check in-game. Anything touching `pointers.rs`, `base_addresses.rs`, or a widget's
read/write path falls under this.

There is no automated test coverage beyond two TOML parse tests in `config.rs`. A wrong write can
crash the game or corrupt a save, so when a change is speculative, say so plainly.

## Known stubs

Worth knowing before you go looking for bugs in them — these are incomplete by design, not broken:

- **Addresses exist for patch 1.03.1 only.** Detection itself is done: `version.rs` reads the running
  module's PE `SizeOfImage`, resolves it to a `Version`, and switches every write off on a build it
  does not recognise. So this is a guard that works, not a gap — but generating address sets for
  other patches is still unfinished.
- `widgets/warp_menu.rs` exists but is not wired into `config.rs`, and is not functional. The
  `wrap_menu` *flag* (a typo for warp, kept for config compatibility) does work.
- `widgets/open_menu.rs` calls game menu functions directly and crashes the game — the AOB signatures
  need revisiting.
- `lib/libdsr/src/lib.rs` has a stray `fn main()`. Harmless, but it is not there for a reason.

## Style

Follow `rustfmt.toml` (inherited from upstream, needs `cargo +nightly fmt`). Match the surrounding
code: `pub(crate)` for cross-module items in `tool`, free constructor functions returning
`Box<dyn Widget>` rather than exposing widget structs, and `hudhook::tracing` macros for logging
inside the DLL (not `println!`).

Keep `libdsr` free of UI and config concerns — it should stay usable by something that is not this
overlay.
